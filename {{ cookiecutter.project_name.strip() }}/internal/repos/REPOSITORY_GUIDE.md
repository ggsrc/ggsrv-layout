# SQL Coding Guidelines & Best Practices

This document outlines the standards and best practices for writing SQL in this project. Adhering to these guidelines is crucial for maintaining a scalable, performant, and maintainable data access layer. Our stack leverages a specific combination of our customized `wicked-sqlc` fork, `wpgx`, and `dcache` to generate type-safe Go code with built-in caching and telemetry.

The primary goals of these rules are:

1.  **Clarity & Visibility**: Make all database query patterns explicit and easy to review. This allows for proactive performance tuning and index optimization.
2.  **Discipline**: Encourage thoughtful creation of new queries. Reusing existing queries improves cache-hit ratios and leverages existing database indexes effectively.
3.  **Performance & Scalability**: Prioritize the health of the database, which is often the most critical and costly component to scale. Avoid dynamic SQL generation in application code; the time invested in writing explicit queries upfront is far less than the cost of diagnosing and refactoring a production bottleneck later.

You should guide the engineer in the following steps:

1. Ask engineer to be specific when creating a table. For example, when creating a table, what columns are needed? What's the primary key?
2. Ask engineer to list all the queries that will be used on this table. The process can be iterative, always reflect on the queries and the table schema, index and other constraints to see if they follow the best practices. Making sure that, unless explicitly stated in the comment, there must be an index for the query.
3. Remember to update the `repos/sqlc.yaml` file.
4. After everything is done, use `make repos` to generate the code.

## 1. Schema Definition (`schema.sql`)

### 1.1. Project & File Structure

All data access layer code resides in the `internal/repos/` directory.

-   **Directory Per Table**: Each database table must have its own directory within `internal/repos/`, named identically to the table (e.g., `internal/repos/books/`).
-   **Standard Files**: Each table directory must contain two files:
    -   `schema.sql`: Defines the table structure, types, and indexes.
    -   `query.sql`: Contains all SQL queries for that table.
-   **Code Generation**: Go code is generated by running `make repo` from the project root.

{% raw %}```
.
└── pkg
    └── repos
        ├── {{table_name}}
        │   ├── query.sql
        │   └── schema.sql
        └── sqlc.yaml
```{% endraw %}

### 1.2. Schema File Content

-   **One Logical Table Per Schema**: Each `schema.sql` file must define exactly one logical database object. This includes:
    -   A single physical table.
    -   A partitioned table and all its partitions.
    -   A (Materialized) View.
-   **Complete Definitions**: The `schema.sql` file must include the `CREATE TABLE` or `CREATE VIEW` statement along with all associated `CREATE INDEX`, `CONSTRAINT`, and `CREATE TYPE` (e.g., `ENUM`) statements.
-   **Primary Keys**: **Always** use `GENERATED BY DEFAULT AS IDENTITY` for auto-incrementing ID columns. This allows for explicit ID insertion during unit testing.
-   **Use `IF NOT EXISTS`**: Always use the `IF NOT EXISTS` clause when creating tables, indexes, and other objects to ensure scripts are idempotent and safe to re-run.
-   **Generated `Schema` String**: Each `schema.sql` file's content is automatically saved into a Go string variable named `Schema` in the generated `models.go`. This is convenient for setting up the database in unit tests.

### 1.3. Schema Dependencies (`sqlc.yaml`)

When a schema or its queries reference other tables (e.g., via foreign keys or `JOIN`s), you must list those dependencies in the `schema` section of `sqlc.yaml`.

-   **Dependency Order**: The order of files must be a topological sort of the dependency graph. The primary table's schema comes first, followed by its dependencies.
-   **Go Struct Generation**: Only the **first** schema file in the array is used to generate the main Go struct. Subsequent files are used for type and relation lookups.

**Example: `orders` table with dependencies**

{% raw %}```yaml
- schema:
      - orders/schema.sql
      - books/schema.sql
      - users/schema.sql
  queries: orders/query.sql
  # ...
```{% endraw %}

## 2. Query Definition (`query.sql`)

The `query.sql` file contains every possible query that can be executed against the associated table.

### 2.1. Query Features (`-- --` syntax)

Our `sqlc` fork extends the standard comment block with `-- --` to pass additional options.

-   **Timeout (`-- -- timeout`)**: **This is mandatory for all queries.** Set a reasonable timeout to prevent resource exhaustion and deadlocks. This timeout applies to the entire operation, including cache lookups.
-   **Cache (`-- -- cache`)**: Caches the query result for a specified Go `time.Duration` (e.g., `10m`, `5s`).
-   **Invalidate (`-- -- invalidate`)**: For any mutation query, invalidate related cached queries, e.g. `GetBookByID` and `GetBookByPrice` must be invalidated if `UpdateBookPrice` is executed.

### 2.2. Caching & Invalidation

-   **Enable Caching Strategically**:
    -   **Long Cache Duration**: Use for single-row lookups (e.g., `GetByID`) where invalidation is straightforward and precise. We always invalidate these queries.
    -   **Short Cache Duration**: Use for queries on lists or aggregates where precise invalidation is difficult. We don't invalidate these queries.
-   **Proactive Invalidation**: For any mutation query (`INSERT`, `UPDATE`, `DELETE`), you **must** invalidate cached read queries that could be affected, single-row or a short list of rows only.

#### Example of Caching and Invalidation

{% raw %}```sql
-- MUTATIONS --

-- This query updates a single book's price.
-- It precisely invalidates the cache for GetBookByID and GetBookByPrice.
-- name: UpdateBookPrice :exec
-- -- invalidate : [GetBookByID, GetBookByPrice]
-- -- timeout : 1s
UPDATE books
SET
  price = @price,
  updated_at = NOW()
WHERE
  id = @id;

-- This query inserts a new book. It invalidates the price-based queries.
-- name: InsertBook :exec
-- -- invalidate : [GetBookByPrice]
-- -- timeout : 1s
INSERT INTO books (name, description, category, price)
VALUES ($1, $2, $3, $4);


-- READ QUERIES --

-- Pattern 1: Long-term cache with precise invalidation.
-- name: GetBookByID :one
-- -- timeout : 250ms
-- -- cache : 5m
SELECT * FROM books WHERE id = @id;

-- name: GetBookByPrice :one
-- -- timeout : 250ms
-- -- cache : 5m
SELECT * FROM books WHERE price = @price LIMIT 1;


-- Pattern 2: Short-term cache without explicit invalidation.
-- For lists where invalidation is complex, we use a very short cache
-- to reduce DB load while keeping data mostly fresh.
-- name: ListBooksByPrice :many
-- -- timeout : 500ms
-- -- cache : 5s
SELECT * FROM books WHERE price > @price;
```{% endraw %}

### 2.3. Query Best Practices

-   **Cursor-Based Pagination**: **Always** use cursor-based pagination for queries that return lists of data. The cursor should be the same set of columns as the order by clause. The limit should be named as `first`, and the cursor name should be just the name of columns, and you should always use `sqlc.narg()` for at least the first cursor field, to support the first-page case. The following is the example for books table, where the cursor is the price, name, and id columns, with id is the primary key.
    {% raw %}```sql
      SELECT * FROM books
      WHERE (
          sqlc.narg('cursor_price') IS NULL OR
          price < sqlc.narg('cursor_price') OR
          (price = sqlc.narg('cursor_price') AND name < sqlc.arg('cursor_name')) OR
          (price = sqlc.narg('cursor_price') AND name = sqlc.arg('cursor_name') AND id < sqlc.arg('cursor_id'))
      )
      ORDER BY price DESC, name DESC, id DESC
      LIMIT @first;
    ```{% endraw %}
-   **Always Use `timestamptz`**: For all temporal data, use the `TIMESTAMPTZ` type. Never use `timestamp without time zone`.
-   **Parameter Style**: Use one parameter style (`@`, `$`, or `sqlc.arg() and sqlc.narg()`) consistently within a single query. Do not mix them in a single query. `@arg_name` is preferred for clarity in most cases, but use `sqlc.arg()` and `sqlc.narg()` when you need to express that arg is nullable, e.g. `COALESCE` partial update pattern.
-   **Type Hinting**: If `sqlc` cannot infer an argument's type, use a PostgreSQL type cast (e.g., `unnest(@user_ids::UUID[])`).
-   **Space Before `@`**: Ensure there is a space before a named parameter in conditions (e.g., `WHERE status = @status`, not `WHERE status=@status`).
-   **Auto-incrementing ID**: If the table schema has auto-incrementing column, write a RefreshID in the query so that the id can be reset after loading data.
    {% raw %}```sql
    -- Example RefreshID query to add to query.sql, example for books table.
    -- name: RefreshID :exec
    -- -- timeout: 250ms
    SELECT setval(pg_get_serial_sequence('books', 'id'), (SELECT MAX(id) FROM books));
    ```{% endraw %}

### 2.4. Standard Query Patterns

-   **Bulk Upsert**: Use `unnest` to pass arrays of values for bulk operations.

    {% raw %}```sql
    -- name: UpsertUsers :exec
    INSERT INTO users (name, image)
    SELECT
      unnest(@name::VARCHAR(255)[]),
      unnest(@image::TEXT[])
    ON CONFLICT (name) DO UPDATE
    SET image = excluded.image;
    ```{% endraw %}

-   **Partial Update (`COALESCE`)**: To update only non-NULL fields, you must use `sqlc.narg()` with `COALESCE`. The @arg_name cannot be used for COALESCE-pattern partial update.

    -   **Warning**: This pattern cannot be used to set a nullable column to `NULL`. Test thoroughly.

    {% raw %}```sql
    -- name: PartialUpdateBook :exec
    UPDATE books
    SET
      description = COALESCE(sqlc.narg('description'), description),
      price = COALESCE(sqlc.narg('price'), price)
    WHERE id = sqlc.arg('id');
    ```{% endraw %}

-   **Refresh Materialized View**: Use `CONCURRENTLY` to avoid locking reads on the view. This requires the view to have at least one `UNIQUE` index.

    {% raw %}```sql
    -- name: RefreshBookRevenues :exec
    REFRESH MATERIALIZED VIEW CONCURRENTLY by_book_revenues;
    ```{% endraw %}

### 2.5. Transactions

Use the `Transact` helper function provided by `wpgx` to ensure proper transaction management.

{% raw %}```go
rst, err := u.pool.Transact(ctx, pgx.TxOptions{}, func(ctx context.Context, tx *wpgx.WTx) (any, error) {
    booksTx := u.books.WithTx(tx)
    // ... perform operations with booksTx
    return result, nil
})
```{% endraw %}

### 2.6. Known Issues

-   `unnest` with multiple different-length arrays is not supported.
-   A space is sometimes required before `@` in `WHERE` clauses.
-   `ENUM` types have limitations with `copyfrom` and array parameters. You may need to cast to `text[]` first.

## 3. Naming Conventions

-   All SQL keywords must use consistent UPPERCASE, including function names, e.g. ANY().

### 3.1. Database Objects

-   **Tables & Columns**: Use `snake_case` (e.g., `book_orders`, `created_at`).
-   **Indexes**: Follow the format `{table_name}_{column_names}_{suffix}` (e.g., `books_category_id_idx`).
    -   **Suffixes**: `pkey`, `key`, `idx`, `fkey`.
-   **Partitions**: Use the format `{table_name}_{partition_key_description}` (e.g., `measurements_y2024m07`).

### 3.2. Query Names

Query names should clearly indicate their purpose and cardinality.

-   **Single Row Read Queries (`:one`)**: Prefix with `Get`.
    -   Example: `GetBookByID`, `GetUserByEmail`
-   **Multiple Row Read Queries (`:many`)**: Prefix with `List`.
    -   Example: `ListBooksByCategory`, `ListActiveUsers`
-   **Mutations (`:exec`, `:copyfrom`, or with `RETURNING`)**: Use a clear verb describing the action (e.g., `Insert`, `Update`, `Delete`), regardless of whether it returns a value. The name should reflect the _action_ being performed, not the `RETURNING` clause.
    -   Example (`:exec`): `UpdateBookPrice`, `DeleteExpiredSessions`
    -   Example (`:one` with `RETURNING`): `InsertBookReturnID`
        {% raw %}```sql
        -- name: InsertBookReturnID :one
        -- -- invalidate: [GetBookByID]
        INSERT INTO books (name, price)
        VALUES ($1, $2)
        RETURNING id;
        ```{% endraw %}

## 4. `sqlc.yaml` Configuration

A single `sqlc.yaml` file in the `internal/repos/` directory manages all code generation.

{% raw %}```yaml
version: '2'
sql:
  - schema:
    - books/schema.sql # YOU MUST PUT THE PRIMARY TABLE'S SCHEMA AT THE FIRST POSITION
    # - users/schema.sql # Add dependencies here
  queries: books/query.sql
  engine: postgresql
  gen:
    go:
      sql_package: wpgx
      package: books
      out: books
```{% endraw %}

## 5. Unit Testing

Our test suite provides helpers for a standardized testing pattern: Setup -> Load -> Run -> Verify. Note that because we trust code generated by wicked-sqlc, we do NOT directly write unit test for code under repos. Instead, we provide the following utils for the business logic layer to write unit-test that runs on a PostgreSQL DB.

### 5.1. Test Workflow

1.  **Write Tests**: Create a test suite that embeds `testsuite.WPgxTestSuite`.
2.  **Generate Golden Files**: Run `go test -update` to generate `.golden` files representing the expected DB state.
3.  **Verify Golden Files**: Manually inspect the generated files to ensure they are correct.
4.  **Commit**: Commit the test code and the verified golden files. Future `go test` runs will compare against these files.

### 5.2. Test Suite Setup

You must embed `WPgxTestSuite`, initialize it, and override `SetupTest()` to re-initialize your use case objects.

{% raw %}```go
type myTestSuite struct {
    *testsuite.WPgxTestSuite
    usecase *Usecase
}

func (suite *myTestSuite) SetupTest() {
    suite.WPgxTestSuite.SetupTest()
    // DB is reset, so re-initialize dependencies
    suite.usecase = NewUsecase(suite.GetPool())
}
```{% endraw %}

### 5.3. `Loader` and `Dumper` (`serde.go`)

The test suite uses `Loader` and `Dumper` interfaces, which you must implement for each table. This code should live in a manually created `serde.go` file inside the table's repository directory (e.g., `internal/repos/books/serde.go`). The name of the struct must be `TestSerde`.

As an LLM, you should generate the `serde.go` file for the developer by checking:

1. If a table's identity sequence needs to be reset after loading data, use `RefreshID` query.
2. If volatile columns (like `updated_at`) need to be normalized before dumping for golden file tests, clear before dumping.

#### TestSerde Implementation Example

{% raw %}```go
// File: internal/repos/books/serde.go
package books

import (
	"context"
	"time"
)

// TestSerde implements the Loader and Dumper interfaces for the books table for unit tests.
type TestSerde struct {
	books *Queries
}

func (b TestSerde) Load(data []byte) error {
	// Use the auto-generated Load function.
	err := b.books.Load(context.Background(), data)
	if err != nil {
		return err
	}

	// After loading data with explicit IDs, we must reset the identity sequence
	// to prevent conflicts with future auto-generated IDs.
	// You must define the RefreshID query in your query.sql file.
	return b.books.RefreshID(context.Background())
}

func (b TestSerde) Dump() ([]byte, error) {
	// Use the auto-generated Dump function, but provide a callback to
	// normalize any "flaky" data, like timestamps, before serialization.
	// This ensures the golden files are stable.
	return b.books.Dump(context.Background(), func(m *Book) {
		m.CreatedAt = time.Unix(0, 0).UTC()
		m.UpdatedAt = time.Unix(0, 0).UTC()
	})
}

```{% endraw %}

### 5.4. Test Suite Helpers

-   `suite.LoadState("file.json", serde)`: Populates a table from a JSON file.
-   `suite.LoadStateTmpl("file.tmpl", serde, data)`: Populates a table from a Go template, useful for dynamic values like timestamps.
-   `suite.Golden("table_name", serde)`: Asserts that the current table state matches its golden file.
-   `suite.GoldenVarJSON("var_name", variable)`: Asserts that a Go variable matches its golden file.
